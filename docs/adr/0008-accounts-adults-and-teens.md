# Accounts: Adults and Teens sign in as Eaters

Emu is served on the public internet at `menu.bamk.eu`, no longer behind Tailscale, so ADR 0005's "add accounts before anyone outside the household can reach emu" has come due. This supersedes ADR 0005. There is no basic-auth stopgap: emu does not go live until this lands.

**Who signs in.** An Account belongs to one Eater and signs in with that Eater's name (any case) and a password. Its Role, Adult or Teen, is set by an Adult and kept apart from the Eater's Category, so moving someone from Teen to Adult does not change their calories, and the reverse. A Child is an Eater with no Account, looked after by an Adult. An Adult changes everything, including Accounts. A Teen sees everything, marks Meals cooked or not cooked, changes their own dislikes and diet (not allergies, allergens, Category or calories, which decide what is safe to serve and are a parent's call), changes their own password and signs out. Rejected: the Role following the Category (it couples permissions to calories) and Accounts apart from Eaters (then "their own preferences" needs another link).

**One guard for every route.** `auth.guard` is a dependency of the whole app, so a route added later is protected without anyone remembering to. Signed out, every route but `/sign-in`, `/healthz` and `GET /disclaimer` answers 303 to the sign-in page (never 401, which the Server's uptime monitor would count as down); static files are not routes and stay public. A Teen may POST only to a short list of route patterns; everything else that changes data is for Adults, so a new route defaults to Adult-only. FastAPI's generated `/docs` and `/openapi.json` are off. A test enumerates every route and checks each redirects when signed out.

**Passwords and sessions.** Passwords (10 to 200 characters) are argon2id hashes at OWASP's minimum cost (19 MiB, 2 passes), and at most two are hashed at once: anyone can start a sign-in, and a load test with twenty at once took the container from 77 to 255 MiB until the cap (148 MiB with it, together with `MALLOC_ARENA_MAX=2` in the image). A session is a random token in a cookie that is `Secure`, `HttpOnly` and `SameSite=Lax`, kept 30 days; Postgres keeps only its SHA-256, with the session's CSRF token. Signing out deletes the session, a new password ends all of that account's sessions (but the one that changed its own password), and removing an Eater removes their Account. Rejected: a signed cookie, which cannot be ended one session at a time.

**CSRF.** Every POST must carry the session's token, in a hidden `csrf_token` field (every form that posts has `{{ csrf_field() }}`, which a test checks) or an `X-CSRF-Token` header, which the pages' scripts read from `<meta name="csrf-token">`. The sign-in form, before there is a session, uses a double-submit cookie. `SameSite=Lax` is a second layer, not the only one.

**Guessing.** Failed sign-ins are counted by the name tried, whether or not it has an Account. After 5, the next try must wait 30 seconds, doubling with each failure up to 15 minutes; a success clears the count. An unknown name is checked against a dummy hash, so it takes as long and says the same as a wrong password. There is no limit by address: behind the Server's proxy emu would have to trust forwarded headers to know it.

**The first Adult.** On a fresh install nobody can sign in, so `python -m emu_the_menu.accounts create-adult NAME` (run in the container, password from a prompt or `--password-stdin`) makes the first Adult, using the Eater of that name if there is one. It refuses once any Adult exists; after that Adults add Accounts in the app. `reset-password NAME` sets a new password for any Account when nobody can sign in. Nothing on the internet can create an Account without one. To bring over the Pi's data, import it first: the importer refuses a database that already has Accounts. The last Adult cannot be removed or made a Teen. Rejected: a first-run page, which whoever reached the new public address first would own.
